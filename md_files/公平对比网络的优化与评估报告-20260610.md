# 在缺少权威 Benchmark 时，如何公平优化对比网络并增强论文说服力

## 1. 报告目的

这份报告回答的问题是：

当研究目标是证明“主网络”优于若干对比网络，但领域内又缺少公信力很强的统一 benchmark 时，作者应该如何优化主网络之外的对比网络，才能让比较尽可能公平，并使论文更有说服力。

下文的结论综合了机器学习方法学文献、模型比较文献，以及与你课题更接近的工程/地震响应预测文献。其中有一部分是文献直接支持的共识，另一部分是基于这些文献对你当前课题场景做出的推论性建议，我会明确区分。

## 2. 核心结论

最重要的结论不是“把所有 baseline 都调到最强”，而是：

1. 不能只精细优化主网络，而让对比网络停留在默认参数或随手设置。
2. 不能把架构改进、训练技巧改进、输入表征改进混在一起，只报告一个最终分数。
3. 在没有统一 benchmark 时，论文的说服力主要来自“实验协议是否受控、透明、可复现”，而不只是最终数值是否更高。
4. 最有说服力的做法通常不是单表比较，而是同时给出两类结果：
   - `受控公平比较`：相同数据、相同信息、相同评价协议、相近调参预算。
   - `best-effort 实用比较`：允许各架构使用其最合理的输入表征和训练配置，但要如实报告预算和代价。

换句话说，如果你的主模型赢在“训练 recipe 更强”或者“输入表示更有利”，那也可以是贡献，但它不能被包装成“纯架构优势”。

## 3. 文献中最常见、也最能服人的 baseline 优化手段

## 3.1 使用统一的数据切分、预处理和评价指标

这是最基本的底线。Gorishniy 等和 Grinsztajn 等在 tabular/DL 对比中都强调，不同论文往往因为 benchmark、预处理和 tuning protocol 不一致而难以比较，因此他们采用统一协议做大规模比较。[1][2]

对你的课题，这意味着至少要统一：

- 训练/验证/测试划分
- 归一化或标准化方式
- 输入时窗长度、采样率、标签定义
- 早停准则
- 主指标与次指标

如果某个对比网络必须使用不同输入形式，比如 `2D-CNN` 用时频图、`LSTM/WaveNet` 用时间序列、树模型用统计特征，那么论文里应明确说明：

- 这是“架构原生输入”的 `best-effort` 比较；
- 该结果不能被解释为“仅由 backbone 架构造成的差异”。

## 3.2 对每个 baseline 单独调参，而不是共用一套“方便”的参数

这一点在优化器、架构、tabular 模型比较文献里都非常一致。Feurer 和 Hutter 的 HPO 章节将调参视为现代 ML 的基本组成部分，而不是可选附属步骤。[3] Bergstra 和 Bengio 也说明，随机搜索通常比网格搜索更有效，至少应把系统调参作为公平比较的标准流程。[4]

更直接的证据来自：

- Sivaprasad 等指出，公平比较必须把“找到好超参数的成本”也纳入考虑。[5]
- Schmidt 等在优化器 benchmark 中显示，不同优化器在不同任务上的表现差异很大，默认参数下的排序并不稳定。[6]
- Gorishniy 等在 tabular DL 综述性比较中，明确采用统一的 training and tuning protocols 来比较不同架构。[1]

因此，对比网络不应只做“能跑起来”的设置，而应至少做：

- 依据原论文和强公开实现来定义搜索空间；
- 对每个模型独立搜索其关键超参数；
- 使用同一种 HPO 框架，如 `random search`、`TPE`、`BOHB`。

## 3.3 用“相近预算”而不是“看起来一样的 trial 数”来保证公平

如果各模型单次训练成本差异很大，只规定“每个模型 30 次 trial”并不一定公平。Sivaprasad 等强调，公平评估要把 tuning cost 也计算在内。[5] Falkner 等提出的 `BOHB` 则说明，在昂贵模型上，多保真/早停式 HPO 是更现实也更高效的选择。[7]

对你的任务，更合理的做法通常是：

- `同类模型内`：可用相同 trial 数比较；
- `异类模型间`：更推荐用相同 wall-clock 预算、GPU 小时预算或总训练预算比较。

例如：

- 树模型可以给定固定 CPU 小时预算；
- 深度模型可以给定固定 GPU 小时预算；
- 或者统一采用“每个模型允许完成 N 次完整训练 + 若干次早停试验”的 protocol。

如果你只汇报固定 trial 数，审稿人很容易质疑：是不是某些模型本来就更难调、单次更慢，所以天然吃亏。

## 3.4 同时控制“容量”和“计算量”

如果主模型参数量、FLOPs 或推理时延远高于 baseline，那么即使结果更好，也很难证明优势来自“架构设计”而不是“更大容量”。

近年的公平比较工作很重视这一点：

- Yu 等在 `KAN or MLP: A Fairer Comparison` 中，显式控制参数量或 FLOPs 后再做比较。[8]
- Lu 等比较 DeepONet 与 FNO 时，不仅比较性能，还尽量让两边在实际计算设置下更可比。[9]

因此，最有说服力的论文往往会给出两张表：

1. `matched-capacity`：参数量或 FLOPs 尽量匹配。
2. `best-effort`：每个模型都尽量调到最好。

如果主模型在这两张表里都领先，可信度会明显提高。

## 3.5 强 baseline 不只是换模型，还包括强训练 recipe

Bello 等指出，很多所谓“新架构提升”实际上混杂了训练方法和 scaling 策略的变化，训练和 scaling 有时比架构改动本身更重要。[10] He 等在视觉任务中也专门强调，公平比较时，baseline 不能被锁死在旧的 fine-tuning 方式上，而应给予合理的同步训练设置。[11]

这对你尤其重要，因为你的对比对象既有树模型，也有 MLP、LSTM、WaveNet、2D-CNN。对这些模型，合理的 baseline recipe 通常至少包括：

- 合适的优化器候选
- 学习率和权重衰减搜索
- batch size 搜索
- scheduler 搜索
- dropout / regularization 搜索
- early stopping
- gradient clipping
- 模型专属结构超参数搜索

如果主网络用了更先进的 scheduler、正则化、归一化、损失函数，而 baseline 没有得到同等对待，审稿人通常会认为比较不够公平。

## 3.6 多随机种子重复，而不是“挑最好一次”

Henderson 等、Colas 等、Picard 都表明，深度学习实验对随机性敏感，少量 seed 或挑选偶然优 seed 会误导结论。[12][13][14]

这意味着：

- 不能用“主模型最好 seed”对比“baseline 的单次结果”；
- 不能只报告单次最优结果；
- 最好报告 `mean ± std` 或 `95% CI`。

如果计算资源允许，经验上更有说服力的是：

- 至少 `5` 个随机种子；
- 更理想是 `10` 个随机种子；
- 如果只做 `3` 个种子，最好在正文解释预算限制，并把它视为偏弱证据。

## 3.7 做统计检验，而不是只看谁的均值更高

单次提升很容易落在随机波动范围内。Dietterich 和 Demsar 等经典工作都指出，算法比较需要适当的统计检验。[15][16]

对于你的场景，可分两类：

- `单数据集、多次重复训练`：可以对多 seed 结果做配对检验，报告置信区间。
- `多结构/多工况/多子任务`：可以把每种工况看作一个任务单元，再用 Wilcoxon/Friedman 一类方法比较。

如果你只有一个测试集，没有公共 benchmark，那么非常建议补充：

- 多随机种子；
- 多结构类型；
- 多地震输入强度；
- 多噪声/分布扰动；
- 关键 tail 区间的分层评价。

这样可以把“一个数据集”扩展成“多个评价场景”，增强统计可信度。

## 3.8 同时报告整体误差和任务关键误差

工程预测任务里，只报告一个整体 MAE 往往不够。你的场景涉及地震响应预测，低漂移区、峰值区、极端响应区的重要性并不一样。

从论文说服力角度，最好的做法是：

- 预先声明一个 `primary metric`，例如以你最关注的 `selection score` 或 tail-sensitive 指标为主；
- 同时报告 `R2 / MAE / RMSE / MAPE`；
- 再补充 `tail MAE`、`extreme underprediction`、`bias` 等与工程风险更相关的指标。

这样做的好处是，审稿人能区分：

- 主模型到底是“总体更好”；
- 还是“只在少数极端样本更好”；
- 还是“整体略差，但关键风险区更稳健”。

## 3.9 公开搜索空间、预算、最优配置和失败案例

缺少权威 benchmark 时，透明度本身就是说服力的一部分。Lu 等在公平比较神经算子时强调 FAIR 原则。[9] Grinsztajn 等甚至公开了大量随机搜索原始结果，以便后续研究者在固定 HPO 预算下复用 baseline。[2]

所以论文最好在附录或仓库里公开：

- 每个 baseline 的搜索空间
- 搜索算法
- trial 数或 wall-clock 预算
- 早停策略
- 最优超参数
- 多 seed 原始结果
- 失败 trial 或不稳定现象的处理方式

这会大幅减少审稿人对“选择性汇报”的担心。

## 4. 针对你当前课题的具体建议

下面这一部分不是文献逐句给出的固定模板，而是基于上面的方法学文献，对你当前这类“多种异构网络比较地震响应预测”的更适合做法。

## 4.1 采用“双轨比较”而不是单轨比较

### 轨道 A：受控公平比较

目的：证明你的主网络在尽量排除输入与训练技巧干扰后，架构本身仍然有优势。

建议做法：

- 所有深度模型尽量使用同一份信息源。
- 如果输入本质上是 `波形 + 标量特征`，那么 MLP/LSTM/WaveNet/主网络都应共享这套信息。
- 若 `2D-CNN` 必须使用时频图，则应说明它使用的是同一原始信号的等价变换，而非额外信息。
- 统一 loss、数据切分、early stopping 逻辑、主评价指标。
- 尽量做参数量或 FLOPs 匹配。

### 轨道 B：best-effort 实用比较

目的：证明在工程实践里，主网络不仅理论上公平占优，而且在“每个模型都被认真调过”的前提下仍然更强。

建议做法：

- 每个模型允许使用最适合自己的输入表征和训练策略；
- 但必须报告各自调参预算与资源消耗；
- 结果里同时列出参数量、FLOPs、训练时长、推理时延。

如果主模型在轨道 A 和轨道 B 都领先，论文会很有说服力。

## 4.2 对你现有模型族，建议至少这样优化 baseline

### 树模型：`RandomForest / XGBoost / LightGBM / CatBoost`

这些模型不能只用库默认值。建议至少搜索：

- `n_estimators`
- `max_depth`
- `min_child_weight` 或 `min_samples_leaf`
- `subsample`
- `colsample_bytree` / `max_features`
- `learning_rate`
- `l2 regularization`
- 必要时加 `early_stopping_rounds`

由于树模型训练快，建议给它们更充分的 HPO 预算，但同时如实报告其 CPU 时间。

### `MLP`

建议至少搜索：

- 层数与宽度
- dropout
- learning rate
- weight decay
- batch size
- activation
- normalization
- scheduler

很多论文低估了 MLP baseline 的上限。[1]

### `LSTM / WaveNet / 2D-CNN`

这三类模型尤其不能只调学习率。建议各自保留结构专属搜索：

- `LSTM`：hidden size、层数、dropout、attention 维度、sequence length、gradient clipping
- `WaveNet`：层数、通道数、dilation 设计、kernel size、dropout、residual/skip 宽度
- `2D-CNN`：输入分辨率、通道数、卷积块深度、kernel size、dropout、projection/fusion 宽度

如果某个 baseline 因显存限制无法探索与主模型同等大的空间，应在文中说明这是硬件约束，而不是算法能力约束。

## 4.3 预算设计建议

这是我基于文献和你当前项目形态给出的建议，不是固定标准。

对于异构模型，更推荐以下预算逻辑：

1. `统一搜索框架`
   - 例如都用 `Optuna TPE` 或 `BOHB`。
2. `统一资源口径`
   - 深度模型按 GPU 小时预算；
   - 树模型按 CPU 小时预算；
   - 附录里同时报告完成 trial 数。
3. `统一早停原则`
   - 基于同一 validation 主指标；
   - patience 尽量一致，或给出等价规则。
4. `统一重复次数`
   - 最终最好配置都用同样的 seed 数复测。

如果资源有限，我更推荐：

- 先做 `低预算全模型搜索`；
- 再对前景最强的 baseline 做 `二阶段加密搜索`；
- 但这套二阶段规则必须对主模型和 baseline 一视同仁。

## 4.4 没有强 benchmark 时，建议自己构造“场景 benchmark”

这往往比只做一次 train/test split 更能打动审稿人。

你可以把测试拆成多个场景：

- 不同结构类型
- 不同楼层数或自由度
- 不同地震强度水平
- 不同频谱特征
- 不同响应区间，尤其是 tail / extreme region
- 不同噪声扰动或输入缺失条件

然后把每个场景都作为一个评价单元，报告：

- 平均排名
- 胜率
- 平均改进幅度
- 显著性检验

这种做法虽然不是公共 benchmark，但已经接近“自建 benchmark protocol”，说服力会远高于单场景分数。

## 5. 论文里最建议出现的三张表

## 表 1：受控公平比较

列建议包括：

- 模型
- 输入信息是否相同
- 参数量
- FLOPs
- 主指标
- MAE / RMSE / R2
- 多 seed 均值与标准差

## 表 2：best-effort 实用比较

列建议包括：

- 模型
- 最优配置来源
- HPO 预算
- 训练时长
- 推理时延
- 主指标
- 次指标

## 表 3：稳健性与 tail 指标

列建议包括：

- 模型
- tail MAE
- extreme underprediction
- bias
- 分场景平均排名

如果你只给一张“最终结果表”，审稿人很难判断提升到底来自哪里。

## 6. 论文中可以直接借用的方法表述

下面这段话可以直接改写后放进论文方法部分：

> 为避免将训练策略优势误判为架构优势，我们对所有对比模型采用统一的数据划分、预处理、验证指标与早停准则，并对每个 baseline 在其原论文与公开强实现所支持的合理超参数范围内进行独立优化。对于异构模型，我们同时报告两类结果：一类是在尽量统一输入信息、容量和评价协议下的受控公平比较；另一类是在各模型采用其最适合的输入表征与训练配置下的 best-effort 实用比较。最终结果均基于多随机种子重复实验汇报均值与离散程度，并辅以统计检验，以减少由于随机初始化、数据切分和选择性调参带来的偏差。

## 7. 不推荐的做法

以下做法很容易被审稿人质疑：

- 主模型做大规模 HPO，baseline 只用默认参数
- 只汇报单次最优 seed
- 主模型和 baseline 使用不同数据切分
- 主模型使用更强输入信息，但不说明
- 只比较最终精度，不比较参数量、FLOPs 和时延
- 只看均值，不报告方差或置信区间
- 只做一种测试场景

## 8. 最终建议

如果你的目标是“让文章更有说服力”，我最推荐的策略不是继续无限堆新模型，而是把比较协议升级为下面这套结构：

1. `统一协议下的强 baseline`
2. `参数/FLOPs/时延透明报告`
3. `多 seed + 统计检验`
4. `场景化测试而非单一测试`
5. `受控公平比较 + best-effort 比较并行`

只要这五点做到位，即使没有社区公认 benchmark，文章依然会显得非常严谨。相反，如果 baseline 优化不充分，哪怕主模型结果更高，审稿人也很容易把提升解释为“比较不公平”。
